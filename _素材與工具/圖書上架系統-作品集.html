碩士專題 · SYSTEM DESIGN

智慧型影像辨識
圖書自動上架系統研究與實現

結合嵌入式感測、OCR影像辨識、機器人取放與雲端服務的軟硬整合研究——不需為書籍加裝任何標籤,直接讓系統「看懂」書名,自動辨識、定位並送回正確書架位置,同時提供即時查詢介面。

Logitech C270 + OCR ESP32 + 紅外線感測 CLAHE + 去歪斜校正 OCR 影像辨識 + 模糊比對 LEGO EV3 機器人 LINE Bot 雲端資料庫
5子系統整合(感測/辨識/機器人/通訊/雲端)
2,723筆辨識實驗資料(29種測試條件)
1場全國性學術研討會海報發表
LINE Bot即時查詢使用者介面

研究動機

圖書館歸還上架,一直是人力密集的環節

圖書歸還後,館員需要人工判讀書名、查找正確位置再重新上架,流程繁瑣且容易出錯。這個研究嘗試用一套低成本的軟硬整合系統,把「辨識書籍」到「送回書架」的流程自動化。

系統以兩條獨立的硬體路徑運作:還書端由主機(Windows 11 + Python)透過 USB 連接 Logitech C270 攝影機,每約 1.5 秒擷取一次畫面,經 OpenCV 前處理與 Tesseract OCR 辨識書背文字,再用 Levenshtein 距離模糊比對找出最接近的正確書名;另一端則由 ESP32 + 9 顆紅外線感測器監控 3×3 書架格位狀態,兩端互不直接溝通,全部透過雲端資料庫的旗標欄位同步——全程不需要為書籍加裝條碼或 RFID 標籤。

確認書籍身分後,由 LEGO EV3Dev 機器人載具執行取件、移動、對接書架、送入等實體動作;雲端資料庫(PHP+MySQL)即時更新館藏狀態,使用者則可透過 LINE Bot 查詢書籍目前位置與狀態。

系統設計

四個功能層,各自解決一個問題

感測與辨識層

不貼標籤,直接「看」書名

捨棄條碼/RFID 需逐本貼標、標籤易褪色毀損的做法,改用 Logitech C270 USB 攝影機直接辨識書名本身,不需依賴 ESP32 觸發。影像前處理管線:灰階(Y=0.299R+0.587G+0.114B)→雙三次插值放大 1.5×→CLAHE 8×8 區塊局部對比強化(clipLimit=2.0)→Otsu 二值化抓書卡輪廓做去歪斜校正,再交由 Tesseract OCR 辨識文字,最後以 Levenshtein 編輯距離正規化相似度(門檻 0.60)做模糊比對,容忍 OCR 誤判 1~2 字。

  • 去歪斜實測:23° 傾斜未校正僅 3.3% 辨識率,校正後回升至 95%
  • 2723 筆辨識資料、涵蓋 29 種測試條件,全程寫入 OCR_LOG 可追溯
  • 刻意不採 Otsu 二值化做前處理(見下方設計取捨)
機器人取放層

樂高教育套件,刷成能連網的 Linux 機器人

將 LEGO EV3 刷成 EV3Dev(Linux 系統),改用 Python 撰寫控制邏輯並直接連線查詢雲端資料庫。四顆馬達分工:X 軸水平移動、Y 軸升降、對接馬達推出/收回、滾輪馬達撥書入架。定位不靠昂貴的編碼器或室內定位系統,而是在地面/書架貼色塊,用顏色感測器邊走邊數色塊格數——免編碼器、簡單可靠、成本低。

  • 色塊計數定位,X/Y 軸共用同一套計數邏輯
  • 對接後以紅/綠色塊二次確認對準,反射光感測器確認書已送入書架
  • 輪詢資料庫 status 欄位,確認變更為 on 才算歸位完成
使用者互動層

免裝 App,LINE 就能查書、取書

後端 Django + Ngrok 建立 HTTPS 通道,前端以 LINE Messaging API 的 Carousel 選單互動,讀者不需要額外安裝任何 App。指令設計不只「查詢」,還涵蓋借閱、排行與 AI 客服。

  • 「找-書名」→ 模糊比對選單 → 回覆所在書架位置
  • 「拿-書名」→ 比對 + 二次確認 → 觸發載具取書
  • 「查詢館藏」回報在架總數;「作者-名」列出該作者館藏(每 10 本分頁)
  • 「熱門書籍排行」讀取借閱排行表;「問-」串接 AI 客服問答
硬體與資料層

單一資料表 + 旗標接力,四端鬆耦合

感測電路以 Altium Designer 設計並手工雕刻 PCB,搭配 3D 列印客製外殼整合模組;核心設計是用一張 DATA 表當唯一資料來源(書名、座標、status、wait/take/put 等旗標欄位),影像辨識、EV3、ESP32、LINE Bot 四端互不直接溝通,全部透過 PHP API 讀寫同一張表的旗標「接力」溝通——任一端故障不會卡死其他端。另設 OCR_LOG 實驗記錄表與 BORROW_RANK 借閱排行表。

  • 旗標接力:辨識設 wait='ok' → EV3 收到出發 → 紅外線改 status='on' → LINE 查 status 回報位置
  • 四端資料庫存取 <200ms、LINE 回應約 0.5~1 秒
  • PHP + MySQL 雲端資料庫,部署門檻低、跨平台皆可串接

研究成果

用數據驗證辨識穩定度,而不只是「做出來會動」

全程自動記錄至 OCR_LOG,累計 2,723 筆辨識資料,涵蓋 29 種測試條件,具可追溯性與可重現性。以下是六項關鍵變因的實測結果。

這正是系統加入 Levenshtein 距離模糊比對的原因——當 OCR 辨識結果不完整或有錯字時,仍能對照資料庫校正回最接近的正確書名,把整體可用性從「靠運氣」拉到「可預期」。模糊比對門檻(0.60)也是從這批實測數據調參得出,不是憑感覺訂的參數。

設計取捨與研究限制

誠實面對:哪些做法被我否決了、系統還有哪些限制

好的工程判斷不只是「做出來」,也包含「測過為什麼不這樣做」。以下是實測後的取捨與目前系統誠實承認的限制。

為何不採 Otsu 二值化做前處理

實測發現深色背景會被整片轉黑、書名筆畫被吃掉(Words=0、平均信心度 0%),自動 ROI 裁切也常誤切到書名;最終前處理只保留「放大+灰階+CLAHE(+去歪斜)」,不做二值化與 ROI——這是比較過才捨棄的做法。

為何選 Tesseract,不用雲端 OCR

PaddleOCR/Google Vision 辨識率更高,但一個吃硬體資源、一個要連網且收費;書名多半是單一整塊文字,Tesseract 離線免費、可調 --psm 6 剛好符合需求,故選擇成本較低的方案。

雲端資料庫的已知限制

PHP API 以 HTTP GET 帶 SQL 呼叫,目前僅靠金鑰驗證、沒有注入防護;單表設計大規模擴充有限;依賴網路連線品質。這些是實際存在的技術債,不是我不知道問題所在。

LINE Bot 通道的限制

Ngrok 建立的 HTTPS 通道僅適合開發階段(網址會變動),正式上線需改用固定網址的雲端主機;且整體查詢功能依賴外部 LINE API 的可用性。

EV3 硬體本身的限制

樂高教育套件承重有限,僅適合輕量示範,無法承載真實圖書館等級的書籍重量與運送距離,要落地仍需換成工業級載具機構。

模糊比對門檻是經驗值

0.60 的判定門檻是實測調參後的結果,兼顧準確與容錯,但仍屬經驗值,換一批書名分佈可能需要重新校準,不是放諸四海皆準的常數。
